## 1. 产品定位、目标用户与核心痛点

### 1.1 一句话定位【已确认】

**本产品是一个本地项目台账与一键启动器：把散落在多个根目录下的项目登记成一张可搜索的清单，记住每个项目该怎么跑，点一下就在应用内执行，并保证退出时把这些进程全部收掉。**

它明确**不是**文件搜索器、不是环境管理器、不是 IDE、不是终端替代品。

### 1.2 核心痛点【已确认，强度待验证（H1）】

开发者的项目分散在「克隆来的」和「自己建的」两个（或多个）根目录里。反复发生的摩擦有三个：

1. **找不到**：想起某个项目，想不起它在哪。这是「台账」价值的来源。
2. **想不起命令**：启动命令是 `npm run dev` 还是 `pnpm dev`？后端要不要先起依赖服务？这是「命令记录」价值的来源。
3. **不想开终端走流程**：打开文件夹 → 开终端 → cd → 敲命令，约 20~40 秒。

**诚实标注**：第 3 条的摩擦是否构成足够的切换动力，目前唯一证据是产品负责人本人的体感，未经任何外部用户验证。

### 1.3 目标用户【已确认·默认】

- **主用户**：同时维护 10 个以上项目、跨 2 个以上技术栈、无固定 IDE 依赖的独立开发者或小团队开发者。
- **非目标用户**：只维护 1~2 个项目的人（shell alias 足够）；重度依赖 IDE Run Configuration 的人；需要团队共享运行配置的场景（本产品是纯本地单人工具）。

### 1.4 产品边界（明确不做）【已确认】

不做环境管理（不建 `.venv`、不管 Node/JDK/Python 版本、不装依赖、不改锁文件）；不做磁盘全盘扫描；不做 GitHub 克隆；不做多机同步；不做团队协作；不做代码展示与编辑。

## 2. 核心功能、业务规则与 MVP 范围

### 2.1 数据模型【已确认】

```
AppConfig
├─ schemaVersion: 1
├─ settings
│   ├─ defaultShell          // 按平台检测，全局可改
│   ├─ loadShellProfile      // 默认 true
│   ├─ trayEnabled           // 默认 false
│   ├─ scanDefaults.maxDepth // 默认 1
│   └─ ignoreNames[]         // 用户可增删
├─ roots[]      { id, path, maxDepth, extraIgnore[], enabled }
└─ projects[]   { id(UUID), type: project|global, path, name, note,
                  detectedStack?, shellOverride?, createdAt,
                  lastRunAt, runCount,
                  commands[] { id, name, commandLine, cwd?, lastRunAt, lastExitCode? } }
```

- **主键与唯一约束**：UUID 作主键（保证重命名/移动后引用不断），规范化后的绝对路径作唯一约束（防止同一文件夹重复登记）。
- **配置只存用户触碰过的内容**：递归扫描出的文件夹是瞬时的、每次重算的，不写入配置。只有当用户给某个扫描结果添加了备注或保存了命令，才在 `projects[]` 创建条目。
- **存储**：单个 JSON 文件，原子写（临时文件 + 重命名），自动备份保留最近 3 份，`schemaVersion` 支持迁移。
- **数据目录**：Windows `%APPDATA%/squirl`；macOS `~/Library/Application Support/squirl`；Linux `~/.config/squirl`。**绝不写入项目目录**（验收项 AC8 专门验证）。卸载不清理配置。
- **安全事实（已接受）**：命令以**明文**存于配置，可能包含 token / API key。v1 不加密、不脱敏（脱敏导致用户无法核对命令）。加密需接 DPAPI/Keychain，属 v1.1。

### 2.2 项目发现与列表【已确认】

- 根目录可以是多个；每个根目录**单独设置递归深度，默认 1（只列一级子文件夹），上限 10**。
- 扫描规则：
  - 排除名单按**条目名**匹配，用户可增删。默认名单：`.git` `.idea` `.vscode` `.cursor` `.trae` `.workbuddy` `.workbuddy-ai` `.github` `.zcode` `.lithe` `.vercel` `.playwright-mcp` `node_modules` `.venv` `venv` `__pycache__` `target` `dist` `build` `.next`。
  - 说明：名单中 `.gitattributes` `.gitignore` `.zcodeignore` 为文件项，列表只列目录，这些条目为空操作。UI 允许其存在（无害），文档说明其对扫描无效果。
  - **所有文件夹都列出**，不做「必须有标志文件才算项目」的过滤；标志文件命中时**高亮**（纯 CSS 效果，零额外成本）。标志文件清单：`package.json` `pyproject.toml` `requirements.txt` `pom.xml` `build.gradle` `Cargo.toml` `go.mod` `composer.json` `Gemfile` `*.csproj` `CMakeLists.txt` `Makefile` `.git`。
  - 符号链接跟随，两条硬限制：**已访问真实路径去重防环**；**不跟随指向根目录之外的目标**。
  - 结果**平铺显示 + 相对路径**，不做树形。
  - 累计 500 条时**暂停扫描**，显示已发现数量，提供「继续扫描 / 降低深度 / 取消」。
  - 触发时机：添加根目录时全量扫一次 + 手动刷新按钮；**不做文件系统监听**。
  - 性能目标：500 项扫描 < 1 秒，扫描异步执行、不阻塞界面。

### 2.3 命令记录规则【已确认】

- **显式保存**：用户在命令输入框填写 → 运行 → 应用提示「保存为启动命令」并预填名称 → 用户确认后入库。**不做偷偷记住上一次键入。**
- 填了命令但不保存：视为临时运行，运行结束提示一次「本次命令未保存，是否保存？」；不保存则丢弃，不产生任何记录。
- 一个项目下**多条命名命令**，可**同时启动**，各自独立日志与独立停止。
- 保存字段：名称、命令行原文、工作目录（默认项目根，可改）。
- **命令失败也允许保存**，记录 `lastExitCode` 并在列表标记「上次失败」。
- **不做参数占位符**（MVP），全局命令存完整命令行。
- 同一命令重复点击启动（已在运行）：默认阻止并提示，提供「再启动一个」选项。
- 同一项目内命令重名：允许，但给出警告。

### 2.4 全局命令【已确认】

与项目**同一数据实体**，`type: global`，不绑定根目录，工作目录默认用户主目录（可改）。覆盖两个场景：忘了有哪些工具、带固定参数的长命令。

### 2.5 执行模型【已确认：方案 A，应用内执行】

**执行链**：应用 → 解析 shell → 以登录 shell 执行单条命令字符串 → 捕获 stdout/stderr → ANSI 归一化 → 分批推送至 UI 日志面板。

- **Shell 解析**：
  - Windows：优先 `pwsh`（7+，支持 `&&`）→ 回退 `powershell.exe`（5.1，**检测到后必须警告 `&&` 不可用**）→ 回退 `cmd.exe`。
  - macOS/Linux：`$SHELL` → 回退 `/bin/zsh` 或 `/bin/bash`。
  - 可全局修改，可按项目覆盖；设置页显示实际解析到的 shell 路径。
- **加载 profile**：`pwsh -Login -NoLogo`、`zsh -lic`、`bash -lic`。理由：环境一致性优先，不加载 profile 则 `nvm`/`conda`/`brew`/`volta` 全部失效。代价是启动变慢，**验收口径放宽为 5 秒**。
- **profile 噪音**：shell 初始化输出与命令输出分离，日志中加分隔线。
- **进程归属**：子进程在独立进程组内启动。Windows 用 Job Object + `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`（应用被强杀时子树也被收）；Unix 用 `setsid` 建进程组，停止时先 `SIGTERM` 整组、宽限期后 `SIGKILL`。
- **无交互**：MVP 不提供 stdin，不支持 Y/N 确认、交互式登录、`sudo` 密码。检测到疑似等待输入时，显示「该命令似乎等待输入，MVP 不支持交互式命令」并允许强制停止。**这是明确接受的功能损失。**
- **输出呈现**：纯文本 + ANSI 清理；每命令环形缓冲上限 5,000 行 / 2MB，超出丢弃最早内容；日志仅会话内存在，不落盘，应用重启清空；分批推送（约 30ms/批），避免高频输出打爆 IPC。

### 2.6 生命周期与托盘【已确认】

| 场景 | 行为 |
|---|---|
| 托盘关闭（默认） | 关闭窗口 = 退出应用 = 杀死所有由本产品启动的进程 |
| 托盘开启 | 关闭窗口 = 隐藏到托盘，进程继续；**只有托盘菜单「退出」才杀死全部** |
| 单条命令 | 可单独停止，不影响同项目其他命令 |
| 关闭项目详情面板 | **不停止**进程，列表继续标记「运行中」 |
| 命令崩溃（非零退出） | 显示退出码与「失败」状态，**不自动重启** |
| 托盘初始化失败（Linux 常见） | 自动降级为普通窗口应用 + 界面提示，**不阻塞启动** |
| 路径失效 | 列表显示「路径不存在」，提供「重新定位」，命令仍可见但不可运行 |
| 命令状态机 | `idle → starting → running → exited(code) / failed / killed`，四态在 UI 上永远可见 |

**已知技术限制（必须写入用户文档，不得隐瞒）**：应用**异常崩溃**时，Linux 依赖 `PR_SET_PDEATHSIG` 收回子进程，Windows 靠 Job Object 收回，**macOS 无等价机制，子进程可能成为孤儿**。缓解方案（启动时扫描遗留 PID 并提示清理）列为【暂定】，不进 MVP 验收。

### 2.7 MVP 范围清单【已确认】

**进 MVP**：多根目录与递归扫描、项目/文件夹列表、搜索、备注、项目 CRUD、命令记录与运行、多命令并行、日志面板、停止与进程树清理、全局命令、最近使用排序、托盘（默认关闭）、自定义排除名单、每根目录独立深度。

**不进 MVP（v1.1+）**：交互式终端（xterm）、参数模板、自动更新、导入导出、多机同步、端口占用检测与管理、依赖检查、开机自启、技术栈图标、崩溃后 PID 回收、命令级环境变量编辑、Git 状态展示、快捷键系统、URI scheme/CLI 调用、卸载清理选项。

### 2.8 其他默认项【已确认·默认】

单实例运行（二次启动只唤起已有窗口）；日志不落盘且有限额；最近使用排序进 MVP（记录 `lastRunAt`，列表默认按最近使用排）；搜索覆盖项目名、路径、备注、命令名四者。

## 3. 竞争差异化与用户留存逻辑

### 3.1 差异化主张【已确认的表述，市场有效性待验证（H2）】

1. **适用任何技术栈**：不依赖项目声明，只要能在终端跑通一次，就能被记录复用。「识别是猜测，记录是事实」。
2. **项目台账而非文件搜索**：带备注、可搜索、按最近使用排序，解决「我忘了它存在」。
3. **轻量原生**：Tauri，量化指标见 3.2。
4. **三端代码同源**。

### 3.2 「轻量」量化指标【已确认·默认】

安装包 ≤ 10MB；冷启动到窗口可交互 ≤ 2 秒；空闲内存 ≤ 120MB；安装后磁盘占用 ≤ 30MB。

### 3.3 竞品现状与本方劣势（本文档最弱一节，如实记录）

产品负责人在质询过程中**未提供任何竞品调研结论**，仅回答「IDE 太重」。第一轮列出的候选（VS Code tasks/workspace、JetBrains Run Configurations、just/Makefile、Procfile 系工具、PM2、mise/asdf、PowerToys Run、Raycast、已停服的 Microsoft Dev Home）均未经系统评估。

- **替代成本极低**：shell alias 文件、每项目 justfile、PowerToys Run snippet 都能以近零成本实现「记录 + 运行」。本产品可能赢的只有**聚合与检索体验**。
- **护城河接近于零**：产品形态是 UX 聚合，无数据资产、无网络效应、无技术壁垒。
- **结论**：适合作为**开源作品和自用工具**，不适合作为创业项目。若期待商业回报，本方案需重新设计。

### 3.4 留存逻辑【已确认，强度弱，不做美化】

- **唯一真实钩子：台账随时间增值**——项目越积越多，清单越有价值，卸载成本越高。这是数据积累型留存，不是使用频率型留存。
- **次要钩子**：最近使用排序，让「上次用过」成为打开即见的默认视图。
- **结论**：这是**低频工具**（预计每周 3~10 次）。明确不为它加健康面板、统计图表、成就系统等留存装饰。

## 4. 商业模式、成本假设与技术约束

### 4.1 商业模式【已确认】

免费开源，无营收设计，GitHub 分发。**没有商业模式是明确取舍，不是遗漏。** 后果需接受：无资金支持 CI 之外的任何成本、无客服、无双端支持承诺、可持续性依赖维护者个人兴趣周期。

### 4.2 成本假设

| 项 | 成本 | 说明 |
|---|---|---|
| 开发时间 | 30~40 人天（见 6.2） | 最大成本，唯一投入方为产品负责人 |
| GitHub Actions | 0（公开仓库） | 三平台矩阵，含 macOS runner |
| macOS 公证 | 0（v1 不做），$99/年（未来） | 未签名需用户右键打开或 `xattr`，已接受 |

| 长期维护 | 隐性且真实 | 依赖升级、平台 API 变更、issue 响应 |

### 4.3 技术约束【已确认】

- **框架**：Tauri **v2**；**前端**：React + TypeScript + Vite。产品负责人对 Rust 熟练度不设要求，PTY/进程树/平台 API 三块按「边学边做」计时，是工期风险主要来源（R1）。
- **开发机环境已核实（2026-10-27）**：Rust 1.96.1（`x86_64-pc-windows-msvc`）、MSVC 14.38、Windows SDK 10.0.22621、WebView2 155.0.4283.62、Node 24、pnpm 12、PowerShell 7.6、Git 2.49。**Tauri CLI 未安装**，首次构建前补装。
- **分发产物**：Windows NSIS/MSI；macOS DMG（arm64 + x64）；Linux AppImage（优先）+ deb。Linux 前置依赖：`libayatana-appindicator3`、WebKitGTK；GNOME 默认不显示托盘图标（需扩展），是托盘在 Linux 的真实可用性风险。
- **平台验证能力（关键诚实声明）**：**无 macOS / Linux 实机或 VM。** 本文档一切关于 macOS/Linux 的表述仅为「代码可编译、产物随 Release 发布、未经实机验证」。所有验收项**仅在 Windows 上执行**。任何宣传材料不得写成「三端可用」。

## 7. 独立审查记录（v0.9 审查结论，v1.0 已吸收）

**内部矛盾及处理**

1. 原「内置终端首次运行并记住」与「直接启动系统终端」互斥 → 收敛为方案 A（2.5、2.6 节）。若未来想恢复「调用系统终端」，是另一个产品。
2. 排除名单混入文件项（`.gitattributes` 等）→ 列表只列目录，文件项为空操作，UI 允许存在（2.2 节说明）。
3. 「能看多级」与「默认只列一级」→ 统一为「每根目录一个深度值，默认 1」。
4. 托盘进 MVP 与无 macOS/Linux 实机 → 标注未验证风险 + 降级路径（4.3、R5）。
5. 「关闭即结束进程」与托盘隐藏 → 拆为两套语义、两个验收用例（AC4）。
6. 「像点击 exe 一样」与 5 秒启动延迟 → 「一键」指交互次数而非延迟；宣传语禁用「瞬间启动」。

**过度设计削减**

- 技术栈图标：零核心价值 → 已移出 MVP（基线确认项 ③）。
- 每根目录独立深度：对多级扫描噪音控制有用，保留。
- 托盘：按负责人决定保留在 MVP，成本主要在测试矩阵。

**遗漏补入**

重复启动处理（2.3）、关闭详情面板不杀进程（2.6）、profile 输出分离（2.5）、配置损坏恢复（AC9）、macOS 崩溃孤儿进程（2.6 已知限制）、数据目录位置（2.1/4.3）、卸载行为（卸载不清理配置，清理选项列入 v1.1）。

**不可验证描述清理**

- 「三端同时可用」→「Windows 验证可用；macOS/Linux 提供产物、未经实机验证」
- 「轻量」→ 3.2 节四项量化指标
- 「启动快」→ 冷启动 ≤2 秒、首行输出 ≤5 秒
- 「适用任何技术栈」→「只要能在终端跑通一次即可记录」

## 附录 A：产品命名记录与占用终检清单（v1.0.1 新增）

### A.1 定名：Squirl

- **词源与隐喻**：squirrel（松鼠）的变体拼法。松鼠把坚果埋得到处都是、过了很久忘了埋在哪——本产品就是那张「藏宝图」：把散落各处的项目收进一张台账，记住每个项目该怎么跑。
- **选定依据**：七轮命名、54 个候选、三种范式（功能造词系／字典词系／活隐喻系）逐一数据验证后的最优解——隐喻直击产品第一痛点（忘了项目在哪、忘了怎么启动），且命名空间干净：GitHub 头号同名仅 54★ 且跨品类，npm / crates.io 双空闲。
- **已知取舍**：变体拼法偶尔会被当成 squirrel 的拼写错误。应对话术：「Squirl——松鼠的另一种拼法，一只替你记住坚果埋在哪的松鼠。」该话术写入 README 首屏。

### A.2 命名数据记录（2026-10-31 查证）

- GitHub 搜索 `squirl in:name`：80 个结果，头号 zkat/squirl（54★，跨品类）
- npm `squirl`：空闲　|　crates.io `squirl`：空闲
- 标尺说明：npm/crates 对本产品为软信号（MVP 不发布 npm 包、不发布库 crate，桌面应用分发链路为 GitHub Releases → NSIS/DMG/AppImage/deb → 自建 tap/bucket）；硬门槛为 GitHub 仓库名与未来的 brew/scoop manifest 名。
